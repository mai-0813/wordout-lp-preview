# 変更履歴

> 本ファイルは、プロジェクトの更新履歴・改善記録を管理する実務用ドキュメントです。
> 詳細な運用メモが増える場合は、必要に応じて本ディレクトリ内に追加ファイルを作成してください。

## 1. 概要

本ファイルは、WordOut LP Preview の改修・整理・リファクタリングの経緯を記録するための実務用履歴書である。

対象は以下の通り。
- 元ネタの静的 LP
- HTML / CSS / JavaScript の分離と整理
- メンテナンス性向上のための構造改善

本プロジェクトは、AI 生成による初期成果物を、実務で継続利用可能な形へ整理することを目的としている。

## 2. 改修記録

### 2026-08-13

#### 2.1.1 追加対応
- CTA 系の重複を整理し、共通の補助クラスで表現をまとめた
- 表示崩れの検知用に Playwright の最小構成を追加した
- モバイルの横スクロールやヒーローの拡大表示を確認対象に含めた
- Playwright の確認手順を skill 化し、保守時の検証基準を明文化した

#### 2.1 背景
- 元のページは、インライン CSS / JavaScript と base64 埋め込み画像が混在しており、更新や修正のたびに影響範囲の特定が難しかった。
- 画像・スタイル・挙動の責務が分離されていない状態で、運用時の保守性が低かった。

#### 2.2 対応内容
- インラインの CSS を [styles.css](styles.css) に分離
- インラインの JavaScript を役割別に分割
  - [js/site.js](js/site.js)
  - [js/hero-toggle.js](js/hero-toggle.js)
  - [js/feature-lightbox.js](js/feature-lightbox.js)
  - [js/header.js](js/header.js)
  - [js/format-slider.js](js/format-slider.js)
- base64 画像を実ファイル化し、[img/](img/) 配下へ整理
- 重複する共通ロジックを [js/utils.js](js/utils.js) に集約
- README を追加し、プロジェクトの概要と運用方針を明文化

#### 2.3 目的
- AI 生成の初期成果物を、実務で保守しやすい構成へ改善する
- HTML / CSS / JS の責務を明確化し、修正範囲を最小化する
- 変更履歴を残して、後続の編集や引き継ぎを容易にする

#### 2.4 影響範囲
- [index.html](index.html) の構造は維持しつつ、外部参照へ整理
- 見た目の定義は [styles.css](styles.css) に集約
- 画面動作の処理はモジュール単位で分離
- 画像管理は [img/](img/) に集約

#### 2.5 備考
- 現時点では静的サイトのため、ビルド工程は不要
- 画面の挙動は、保守性と可読性を優先して整理済み
- 以後の編集内容は、本ファイルに追記して管理する

## 3. 運用ルール

1. 変更を加えた場合は、原則として本ファイルに要点を追記する。
2. 追記時は、背景・対応内容・影響範囲・留意事項を簡潔に記載する。
3. 実務資料として完成した時点で、必要に応じて `/init` を実行して初期化・整理を行う。
4. README は利用者向けの入口、HISTORY は記録用の詳細情報として役割を分離する。

## 4. 今後の更新方針

- 変更や改善があれば、日付順で追記する
- 実務資料としての明確さを優先し、冗長な説明は避ける
- 既存の構 成や責務を破壊しない範囲で改善を継続する

## 5. 実行順序の判断

今回の整理では、GitHub 運用の skill を作る前に、まず `/init` を行う順序が妥当と判断した。

理由は以下の通り。
- リポジトリの構成とファイル役割を明確化してから、skill の対象範囲を固定したほうが安全である
- README / docs / source の責務が揃っている状態でないと、skill の指示や運用ルールが揺れやすい
- `/init` により基盤の整理が完了してから、GitHub 運用の skill を追加することで再利用性が高くなる

したがって、最適な順序は以下の通り。
1. 最終整理チェックを完了する
2. `/init` を実行する
3. GitHub 運用の skill を作成する
4. 必要に応じて運用ルールを調整する
